# Audit Report — Post Phase 6 (Session 2026-06-09)

## Summary

Phase 6 refactored the entire delivery photo pipeline. The previous design had duplicate data flow (photos going to both `delivery_photos` and the now-removed `promote/mark-processing/ping` cascade), required multiple round trips just to move one photo through Drive, and had no offline queue. The new design is:

**Flow:** `/mark` (creates placeholder `delivery_photos` row, sets status) → staff captures photo client-side → IndexedDB queue stores blob → `/sync-photo` (single upload to GAS webhook + DB update) → queue resolves to `ok`/`orphan`/`retry`

---

## P1 Bugs (Must Fix Before Next Session)

### 1. `incrementRetry` resolves before IndexedDB transaction completes

- **File:** `src/lib/photo-queue.ts:97-98`
- **Bug:** `resolve()` is called immediately after setting up the transaction, NOT in `tx.oncomplete`. The retry count increment may not be persisted to disk when the caller receives the resolved promise.
- **Impact:** If the browser/tab closes between `resolve()` and the actual write, the retry count is lost. A photo can be retried indefinitely beyond `MAX_RETRIES` without being promoted to orphan.
- **Fix:** Move `resolve()` into `tx.oncomplete` callback (same pattern as `removeFromQueue`).

### 2. `sync-photo/route.ts` — No staff ownership validation

- **File:** `src/app/api/deliveries/sync-photo/route.ts:26-38`
- **Bug:** The route verifies the `delivery_photos` record exists and isn't already synced, but does NOT check that the `assignment_item_id` belongs to the requesting user. Any authenticated user can upload to any `deliveryPhotoId` (within UUID guessing or if they know the ID from another source).
- **Impact:** Staff A could overwrite Staff B's photo record (`photo_url`, `synced_to_drive`). Cross-contamination of delivery evidence.
- **Fix:** Add a JOIN/check: `assignment_items -> daily_assignments.staff_id = user.id`.

## P2 Issues (Should Fix Soon)

### 3. `unsynced/route.ts` — No admin auth enforcement for `?all`

- **File:** `src/app/api/deliveries/unsynced/route.ts:41-43`
- **Issue:** The `?all` param is silently ignored for non-admin users rather than returning a 403. Any staff user passing `?all` just gets their own photos (due to the staff_id filter), but this is misleading — an admin could forget to check auth and accidentally expose data.
- **Fix:** Return 403 if `all && !isAdmin`.

### 4. `mark/route.ts` — No server-side GPS target validation

- **File:** `src/app/api/deliveries/mark/route.ts:10-17`
- **Issue:** `targetLat`/`targetLng` are accepted as request body params. The server does NOT validate that these coordinates match the assigned unit's known location. A malicious staff member could pass fake coords to bypass GPS enforcement.
- **Fix:** Query `survey_units` for the PSID's known lat/lng at the start of the route and use those instead of accepting client-provided target coords. GPS enforcement should always use server-authoritative target coordinates.

### 5. IndexedDB schema migration — `deliveryPhotoId` index not created on v3→v4 upgrade

- **File:** `src/lib/photo-queue.ts:20-29`
- **Issue:** `DB_VERSION` was bumped from 3 to 4 when `deliveryPhotoId` was added. But `onupgradeneeded` only creates the store+indexes if the store doesn't exist yet (`!db.objectStoreNames.contains(STORE_NAME)`). Users on version 3 will upgrade to 4 without the `deliveryPhotoId` index being created.
- **Impact:** Queries by `deliveryPhotoId` (if added later) would do a full table scan. Currently not a functional problem since we query by `id` and `assignmentItemId`, but the index is declared yet never actually created for existing installation.
- **Fix:** In `onupgradeneeded`, create indexes unconditionally if they don't exist, not only when the store is first created. Better: use a migration pattern where each version increment adds missing indexes.

### 6. `usePhotoQueue` state duplication across 5 components

- **Components affected:**
  - `unit-delivery-sheet.tsx` — `{ enqueuePhoto, queueCount }`
  - `deliver/page.tsx` — `{ queueCount, isProcessing, processQueue }`
  - `unsent-images-section.tsx` — `{ queueCount, isProcessing, processQueue }`
  - `unsent-badge.tsx` — `{ queueCount, isProcessing, processQueue, refreshCount }`
  - `floating-actions.tsx` — `{ queueCount: unsentCount }`
- **Issue:** Each component instance creates its own local `useState` for `queueCount`/`isProcessing`. When a photo is enqueued in the sheet, the deliver page badge doesn't update until it re-renders for another reason.
- **Impact:** The amber badge "3 photos waiting to sync" can be stale by up to an entire render cycle. The `processQueue` button may show `0` while the sheet just added an entry.
- **Fix:** Move queue state to a React Context provider or a Zustand store. Subscribe to IndexedDB via `db.onversionchange` or periodic `getQueueCount()` polling.

### 7. Toast duration default changed to 12 seconds

- **File:** `src/components/ui/toast.tsx` (duration changed from 4000 to 12000)
- **Issue:** This affects ALL toasts globally — "Staff deleted", "Settings saved", "Data fetched", etc. Non-delivery toasts lingering for 12s are obtrusive.
- **Fix:** Either keep default at 4s and pass `duration: 12000` only for delivery-specific toasts, or create a dedicated `deliveryToast()` helper.

## P3 Observations (Minor / Known Trade-offs)

### 8. `mark/route.ts` — `status === 'processing'` auto-promotes to `delivered`

- **Line 111-112:** If the item is already `processing`, it auto-promotes to `delivered` without GPS enforcement check.
- **Rationale:** Staff already on-location in a prior attempt. Intentional design choice, but could be exploited if the first attempt had a brief GPS spike that passed.
- **Mitigation:** Acceptable. Processing status is set server-side only when GPS was within threshold on first attempt.

### 9. `unsynced/route.ts` double filter may miss edge cases

- **Line 37-38:** Filters by `synced_to_drive = false AND photo_url is null`.
- **Issue:** If a crash occurs *after* `photo_url` is set but *before* `synced_to_drive = true`, the record falls through the cracks — it's not unsynced (because `synced_to_drive = false`) but won't appear in this list (because `photo_url is not null`).
- **Mitigation:** With the new atomic sync-photo route (both fields set in a single `.update()`), this window is extremely narrow. Acceptable.
- **Future:** Remove the `.is('photo_url', null)` filter — it's redundant.

### 10. Deliver page badge stale count

- **File:** `src/app/deliver/page.tsx:190-202`
- **Issue:** The queue count badge is only refreshed on mount. If the `unit-delivery-sheet` enqueues a photo, the badge doesn't increment until a re-render is triggered by navigation or state change elsewhere.

### 11. `geo.ts` — No input validation

- **File:** `src/lib/geo.ts`
- **Issue:** `haversine()` accepts raw numbers with no bounds checking. Passing `NaN`, `Infinity`, or out-of-range values produces nonsensical distances but no error.
- **Impact:** If GPS is briefly `null` → 0 (from DB null-coalescing), distance is computed from lat=0,lng=0 (Atlantic Ocean null island) instead of being skipped. The mark route guards against this at lines 113-114 (null check), but any future consumer is unprotected.

### 12. `sync-photo/route.ts` — Hardcoded email fallback

- **Line 48:** `const email = (item as any)?.daily_assignments?.staff?.email || 'staff@billing.local'`
- **Issue:** If the staff record has no email, the fallback is 'staff@billing.local' — a fake email sent to the GAS webhook. This is cosmetic (used for Drive file metadata) but could confuse downstream processing.

### 13. `force/route.ts` still exists (not deleted)

- **File:** `src/app/api/deliveries/force/route.ts`
- **Status:** Referenced by `unit-delivery-sheet.tsx:224-231` (`forceComplete` function). Not part of the refactored pipeline — a separate admin-only override endpoint.
