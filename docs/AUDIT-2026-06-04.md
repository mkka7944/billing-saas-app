## 2. Debugging Pain Points

**Root cause: layered code with no single index, partial refactors, and no tests.**

| Pain Point | Where It Hurts |
|---|---|
| **No central "where is X implemented" map** | Adding a new field to a survey unit touches: schema → migration → types → API route → repository → hook → component → store → filter. No "owners" file. |
| **Repository layer (R.3) only 60% done** — 4 repos exist (`survey`, `assignment`, `data-insight`, `flagged-psids`). Remaining routes have **inline `.from()` + filter + error handling**. Same bug found in 3 routes (status filter) in Phase E. | When a filter changes, must grep 3+ files. |
| **No tests at all** — 0 unit, 0 integration, 0 E2E. Every fix is verified manually. | Refactors are risky; regressions hide. |
| **`billing-store.ts` has dual state** — `filters` + `pendingFilters` + `selectedCity` + `sort` + `setPageIdentity` + `setSortConfig`. Update → invalidate interactions are implicit. | A new filter doesn't always invalidate the right query keys. |
| **Three sheets for same data** — `house-detail-sheet.tsx`, `unit-delivery-sheet.tsx`, `deliver-bottom-sheet.tsx` (B.16/B.19). Logic duplicated. | Edit one, the other two drift. |
| **Query keys use object references** — `use-survey-data.ts:8`: `['surveys', filters, ...]`. Every render = new `filters` ref = cache miss. (H4/H5 in audit, **not yet fixed**.) | Bug fixes masked by re-fetch. |
| **No `no-explicit-any` lint rule** — `(admin.from('staff') as any).upsert(...)` pattern in 3+ files. | IDE rename fails silently, types lie. |
| **No barrel `index.ts` in `components/` or `lib/`** | Imports break on refactor; find-usages unreliable. |
| **No structured logging** — `console.error` scattered. | "Which user/request failed?" requires reading Next.js stdout. |
| **Inconsistent error shape** — `{data, error}` vs `{error}` vs `{data, total, page}`. | A client fix that works for one route errors on another. |
| **Supabase `server-only` guard not on `admin.ts`** (only `server.ts:1`) | service_role key could be bundled into a client component by accident. |
| **H1/H2/H3 known-bad patterns from Section 15 audit are still in the code** | New devs copy-paste the PSID pagination loop, the unbounded `assignment_items` fetch, the staff-stats fallback. |

**Cost of this:** each "small change" requires the user to (1) recall where logic lives, (2) trust the developer found all copies, (3) re-test every screen that uses it.

## 4. Supabase Egress Analysis (70 Staff, 5 GB Budget)

### Per-Day Footprint (estimated)

| Source | Per-call | Calls/day | Daily |
|---|---|---|---|
| Staff: `/api/assignments?staff_id=X` (50 items × 50 unit joins) | 50 KB | 70 | 3.5 MB |
| Staff: `/api/surveys/payments` per delivery | 3 KB | 50 × 70 = 3,500 | 10.5 MB |
| Staff: `/api/uc-stats`, `/api/staff/stats` (cached 5min) | 30 KB | 70 | 2.1 MB |
| Staff: `/api/bill-months`, `/api/hierarchy` (cached 30-60min) | 6 KB | 70 | 0.4 MB |
| Staff: `/api/auth/profile` | 1 KB | 70 | 0.07 MB |
| **Staff subtotal** | | | **~16 MB/day = 480 MB/month** |
| Admin: `/api/surveys` (with H1 PSID loop, per session) | 5 MB | 5 × 5 = 25 | 125 MB |
| Admin: `/api/data-insight` (H2 unbounded items) | 5 MB | 5 × 10 = 50 | 250 MB |
| Admin: `/api/billing-charts` (RPC) | 30 KB | 5 × 5 = 25 | 0.75 MB |
| Admin: `/api/routes` (batched 1K-page loop) | 3 MB | 5 | 15 MB |
| **Admin subtotal** | | | **~390 MB/day = 12 GB/month** ⚠️ |

### Hard Truth
- **Staff-only use: ~480 MB/month** — safe in 5 GB.
- **With H1+H2 bugs and 5 admins browsing daily: ~12 GB/month** — **2.4× over the free tier.**

### Top-3 Egress Offenders (still unfixed in code)
1. **H1 — `survey-repository.ts:48-63`**: PSID pagination loop fetches ALL 200K+ PSIDs in 3,000-row pages, then chunks to 800 for payment join, then slices. **~5 MB per admin session.** Killing this one saves ~3 GB/month.
2. **H2 — `data-insight-repository.ts:15-19`**: `assignment_items.select(...).gte('delivered_at', ninetyDaysAgo)` — no `.limit()`. After 6 months of use, single load fetches 50K+ rows = 5 MB. Will silently truncate at 1 MB Supabase response cap.
3. **H3 — `staff/stats/route.ts:24-91`**: Fallback path fetches ALL `daily_assignments` + ALL `assignment_items` + ALL `staff` for a date range. Multi-staff stats = 1-3 MB.

### Industry-Standard Mitigations Missing
- **No HTTP cache headers** on `/api/*` responses (everything is `Cache-Control: no-store` from Next.js defaults). Vercel Edge Cache not leveraged.
- **No request coalescing / SWR-style dedup** beyond TanStack Query defaults.
- **No CDN caching for reference data** (hierarchy, bill_months, surveyors) — small but they re-fetch on every page load.
- **No service worker / IndexedDB for delivery data** (only photos are cached).

**Realistic egress after fix:**
- Fix H1+H2+H3: ~3-4 GB/month
- Add HTTP cache headers + Edge Cache on read-only routes: ~1.5 GB/month
- **Still over 5 GB at 70 staff + 5 admins.** Need to either upgrade to Supabase Pro ($25/mo) or aggressively cache.

## 5. Security & Authorization

### 5.1 Authorization — CRITICAL

**Every API route is open to any logged-in user.** The middleware checks "is logged in" but **never checks role**. There is no `requireAdmin()` / `requireRole()` helper. Combined with `USING (true)` RLS policies, this means:

| Endpoint | Risk |
|---|---|
| `POST /api/admin/users` | Any staff can create a new super_admin account. |
| `PATCH /api/admin/users/[id]` | Any staff can change their own role to super_admin. |
| `DELETE /api/admin/users/[id]` | Any staff can delete any user. |
| `POST /api/assignments` | Any staff can create assignments for any city/staff. |
| `PATCH /api/assignments/items` | Any staff can mark **anyone's** delivery as delivered/missed (no `WHERE staff_id = auth.uid()`). |
| `POST /api/delivery/photos` | Anyone with a `assignment_item_id` + fake Drive URL can inject "delivered" photos. |
| `POST /api/admin/flagged-psids` | Any staff can create admin-level flag entries. |
| `GET /api/orphan-psids` | Any staff can dump all orphan PSIDs. |
| `GET /api/staff/performance` (POST) | Any staff can write performance ratings for any other staff. |

**This is a critical data-integrity issue, not just a security one.** Field staff can mark each other's deliveries as complete, faking their own numbers.

### 5.2 RLS Policies

- 9 of 11 RLS-enabled tables have `USING (true)` / `WITH CHECK (true)` — essentially no row-level access control.
- 0 policies use `auth.uid()` for ownership checks.
- 0 policies check role (`is_admin()` / `has_role('admin')`).

### 5.3 Authentication

- Username-based ✅, suspended/deleted check after login ⚠️ (signs out after issuing JWT — wastes a session).
- No 2FA, no rate limiting, no login throttling.
- Password min 6 chars only. No complexity.
- **New password returned in plaintext in API response** (`admin/users/route.ts:131`). Logged in network tab, Vercel logs, browser history.
- Reset password same problem.

### 5.4 Required Hardening (priority order)

1. Add `requireRole(roles)` helper that reads `auth.getUser()` + `profiles` + 403s on mismatch.
2. Apply to all 23 routes.
3. Replace `USING (true)` RLS with role-aware policies (staff sees only own assignments, admin sees all).
4. Ownership check on `assignments/items` PATCH — verify calling user's `staff.id` matches the assignment's `staff_id` and the assigned_date is today.
5. Ownership check on `delivery/photos` POST — same.
6. Pre-check suspended/deleted at login (avoid issuing JWT to invalid accounts).
7. Add login rate limiting (Vercel Edge Middleware + Upstash free tier).
8. Stop returning plaintext passwords in API responses — require admin to type the password twice in the UI.

## 6. Data Integrity

### 6.1 Schema-Level Gaps

1. **No FK from `assignment_items.survey_id` to `survey_units`** — orphan items possible.
2. **`/api/assignments` POST has 2-step insert with manual rollback** — race condition window (`assignment-repository.ts:258-281`). Should be wrapped in a Postgres function or RPC.
3. **`/api/flagged-psids` POST does INSERT then UPDATE** for `flagged_by` — should be one INSERT (`flagged-psids-repository.ts:113-130`).
4. **No unique constraint on `flagged_psids(psid, reason, bill_month)`** — staff can dup-flag.
5. **Soft-delete (`profiles.deleted_at`) doesn't cascade to `staff.is_active`** — drift between tables.
6. **Geography mutable on `survey_units`** — no DB constraint to prevent city_district/tehsil becoming inconsistent.
7. **Legacy triggers potentially dangling** — only one (payment_history) was audited. Others (e.g., on `bill_items` since dropped) may still exist. Audit needed.
8. **`staff_daily_stats` is trigger-maintained** — if trigger fails, stats silently wrong. No fallback / sanity check.
9. **`/api/assignments/items` PATCH accepts `notes` with no length cap** — DoS/storage risk.
10. **No audit log for write operations** — staff deliveries, user creation, role changes are not logged anywhere queryable.

### 6.2 Reference / Pipeline Tables
- `flagged_psids`, `bill_print_log`, `ingest_log` exist (migration 027) but have only `USING (true)` RLS — any logged-in user can read/write.
- `ingest_log` is only written by Python scripts, never by API — no in-app audit trail of mutations.

### 6.3 Required Hardening

1. Add `BEGIN/COMMIT` wrapping or RPC for `createAssignment` and `createFlaggedEntry`.
2. Add unique constraint on `flagged_psids(psid, reason, bill_month) WHERE resolved_at IS NULL`.
3. Add FK `assignment_items.survey_id` → `survey_units.survey_id`.
4. Add text-length CHECK constraints on all free-form text fields.
5. Add `audit_log` table or extend `ingest_log` to capture in-app mutations.
6. Add `is_admin()` and `has_role(text)` SECURITY DEFINER functions in Postgres for RLS use.

| `billing-charts` | ❌ | Manual |

**18 of 23 routes lack Zod or any equivalent validation.**

### 7.2 Specific Risks

1. **Numeric fields not validated** — `gps_lat`/`gps_lng` in `assignments/items` route: `if (gps_lat != null) update.gps_lat = gps_lat` — accepts any number, including out-of-range (-90/90 for lat, -180/180 for lng).
2. **SQL injection via `.or()` strings** — `survey-repository.ts:34`: `qb.or('consumer_name.ilike.%' + q.search + '%')` — Supabase's `.or()` uses PostgREST syntax, not raw SQL, so safe. But if `q.search` contains characters that break the syntax (e.g., commas, parens), it could error or behave unexpectedly. Not validated.
3. **Search inputs not sanitized** — `q.search` goes directly into `.ilike.%${q.search}%`. With `%` or `_` or `\` characters, results are unpredictable.
4. **No length limits on text fields** — `notes` field on assignment_items has no max length. A malicious user could insert a 1GB string and fill the DB.
5. **No UUID format validation** — `id` params from URL (`/api/assignments/items/[id]`) are passed straight to `.eq('id', id)`. If `id` isn't a UUID, PostgREST returns 400, but the error message could leak info.
6. **JSON body parsing is `await request.json()` with no try/catch** — if body is malformed, throws. Some routes have try/catch, some don't.

### 7.3 Required Hardening

- Migrate all 18 routes to Zod.
- Add `gps_lat`/`gps_lng` range checks (`z.number().min(-90).max(90)` / `z.number().min(-180).max(180)`).
- Add length caps on all text fields (`z.string().max(1000)`).
- Sanitize `q.search` for ILIKE wildcards (`%` and `_` and `\` need escaping).
- Use `z.string().uuid()` for all `id` params.
- Wrap all `request.json()` in try/catch and return 400 on parse error.

## 9. Direct Answers

**Q: Why does "simple edits" take many searches?**
A: Layered code (4+ layers: hook → fetch → route → repo → query), partial repository refactor (4 of 8+), no tests, three sheets for the same data, no central "owners" map, no structured logging, inconsistent error shapes, and known-bad patterns from a 6-week-old audit still in the code that new devs will copy.

**Q: What needs to be done keeping industry standard?**
A: Phases 4-6 (debugging velocity + industry standard adoption). The single highest-value item is **CI + tests for the repository layer** — it prevents the bug class that caused 3+ Phase E bugs.

**Q: What is lacking?**
A: Tests, observability, auth, rate limiting, security headers, migration tooling, structured logging, centralized API docs.

**Q: Supabase 5GB free tier with 70+ staff?**
A: **Not safe as-is.** Staff-only: ~480 MB/mo (fine). With 5 admins and H1-H3 bugs: **~12 GB/mo, 2.4× over budget.** Fixing Phase 1 brings it to ~3-4 GB/mo. Phase 6 brings it to ~1.5 GB/mo. **Realistic answer: plan to upgrade to Supabase Pro ($25/mo) once you cross ~1 GB/mo.**

**Q: Security/Auth status?**
A: **CRITICAL — wide-open authorization.** Any logged-in user (including field_staff) can create super_admin accounts, mark any delivery as done, inject fake photos. Middleware checks login but not role. RLS is `USING (true)` everywhere. This must be fixed before real production use by 70 staff.

**Q: Data integrity status?**
A: Several gaps. The two-insert-with-manual-rollback pattern in `createAssignment` is a race condition. `survey_id` on `assignment_items` has no FK. Soft-delete doesn't cascade. No audit log for writes.

**Q: Input validation status?**
A: 5 of 23 routes use Zod (the new `validateQuery` helper). 18 routes have manual `if (!x) return 400` checks — some missing entirely. GPS coords, text length, URL format not validated. Search wildcards unsanitized.
